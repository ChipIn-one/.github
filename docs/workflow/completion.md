# Completion policy

When automation closes a ChipIn Issue as completed. Owner decisions of the completion epic [#177](https://github.com/ChipIn-one/.github/issues/177), task [#179](https://github.com/ChipIn-one/.github/issues/179); the per-repository rule is the top-level `completion` field and `capabilities.completion` of each record in [`workflow-registry.yaml`](../../workflow-registry.yaml).

## Rules

1. **Native Issue state is the completion authority.** An Issue is complete when it is `closed` with `state_reason=completed`; Project #5 `Done` is only a derived mirror and is never completion evidence (see [`github-issue-schema.md`](../../github-issue-schema.md)).
2. **One engine, one strategy per repository.** [`automation/completion.mjs`](../../automation/completion.mjs) reads the registry record and runs only when `capabilities.completion: automatic`; the record's `completion` picks the strategy.
3. **Evidence is the native Development link plus merged PRs.** The engine reads GitHub's native `closedByPullRequestsReferences` (Development links), which GitHub also creates from closing keywords in a PR body; the engine never parses text itself, and plain references, branch names and Milestones are never evidence. Every linked PR must be a same-repository PR (`headRepository` and base repository are the Issue's repository) with readable merge evidence. Project convention: PRs carry a `Task identity:` line and no closing keywords, so the link is created by the development-link reconciler, not by keyword inference.
4. **Fail closed.** Open blockers, incomplete or invisible sub-issues, ambiguous links, unmerged PRs, a scope change after the last merge or unreadable history leave the Issue open with a diagnostic code. Nothing is guessed.
5. **One mutation.** The engine only sets `state=closed`, `state_reason=completed`, after re-reading the Issue (`stale-snapshot` if it changed). It never reopens an Issue and never writes Project Status (the only other Status writers are intake and the opt-in `In Progress` writer of the development-link reconciler, [below](#in-progress-at-development-link)), except the existing repair of an open Issue still showing derived `Done` → `In Progress` and, for `production-merge` and `deployment-receipt`, `Todo`/`In Progress` → `Awaiting release` ([below](#awaiting-release-frontend)), both only when Project reconciliation is on.
6. **Registry rule.** `capabilities.completion: automatic` is valid only with `completion: production-merge`, `integration-merge` or `deployment-receipt` (`AUTOMATIC_COMPLETION_STRATEGIES` in [`registry.mjs`](../../automation/registry.mjs)); anything else fails validation with `REGISTRY_VALUE`. A `deployment-receipt` record must declare `productionEvidence: { environment, creator }` and `deploymentProfile: production`; no other strategy may carry `productionEvidence`.
7. **Status is not an input.** The engine never reads Project Status for its close decision; `Todo`, `In Progress`, `Awaiting release` and `Done` neither allow nor block a close. For `production-merge` and `deployment-receipt` it writes `Awaiting release` after the decision ([#180](https://github.com/ChipIn-one/.github/issues/180), [below](#awaiting-release-frontend)); `integration-merge` never writes it, because the merge itself is terminal.
8. **Schema wording.** [`github-issue-schema.md`](../../github-issue-schema.md) says "Completion triggers per repository are defined by the registry `completion` strategy" and points here (owner-approved in #180).

## Native auto-close and the engine

In `.github` and `chipin-knowledge-base` the integration branch is the default branch, so GitHub itself closes a linked Issue about 2 s after a linked PR merges into it (KB Issues #28, #32, #33, #35 and #41 were closed this way). That native close checks none of the engine's gates: open blockers, incomplete sub-issues and scope changes are ignored.

- The repository setting **Settings → General → Issues → "Auto-close issues with merged linked pull requests"** must be **disabled** in every `integration-merge` repository, so that the engine, with its fail-closed gates, is the only closer.
- Disabling it is an owner action tracked in [#179](https://github.com/ChipIn-one/.github/issues/179); no automation changes repository settings.
- Until it is disabled, GitHub closes first and the engine only acts on leftovers: Issues linked after the merge and Issues whose native close was prevented.

**This page describes the engine with the setting disabled.**

## Strategies

### `production-merge` (frontend rollback record)

No registered repository uses it since [#216](https://github.com/ChipIn-one/.github/issues/216); it stays implemented and tested as the rollback target of the frontend cutover window ([chipin-frontend#497](https://github.com/ChipIn-one/chipin-frontend/issues/497)). Rollback is a `git revert` of the whole #216 commit (registry record, routing, sweep and tests together, giving back `branches: { default: main, integration: dev, promotion: main }`, `completion: production-merge`, `release: semver-by-impact / promotion-merge`, `capabilities.completion: automatic`), never an edit of the registry record alone: the tests assert the live record and the routes derived from it.

A merge to `dev` is integration evidence, not completion. A linked PR is production-complete when its merge commit is contained in the `dev` head snapshot recorded by a merged same-repository `dev -> main` release PR, or when the linked PR is itself the canonical `dev -> main` PR. The engine delegates to [`frontend-production-completion.mjs`](../../automation/frontend-production-completion.mjs) unchanged (rule and scope refinements: [`frontend-production-completion.md`](../../automation/frontend-production-completion.md)). The module is bound to `dev`/`main`; any other branch layout in the registry is refused with `STRATEGY_BRANCH_MISMATCH`. A reopen that undoes an early manual close made after the merge is ignored here, because the release comes later.

### Awaiting release (frontend)

Project #5 Status `Awaiting release` ([#180](https://github.com/ChipIn-one/.github/issues/180)) shows that the work is merged into `dev` and waits for the `dev -> main` release. It is display only: nothing closes an Issue because of it, and the close still follows the production evidence above.

- **Writer.** [`completion.mjs`](../../automation/completion.mjs) (`reconcileAwaitingRelease` / `setAwaitingReleaseStatus`), after the `production-merge` sweep, when Project reconciliation is on and `CHIPIN_COMPLETION_AWAITING_RELEASE=1`. Only the org workflow [`.github/workflows/frontend-production-completion.yml`](../../.github/workflows/frontend-production-completion.yml) sets it, with the org write PAT; the repository-local `frontend-production-completion-action` cannot (a repository token cannot write the org Project). The built-in Project workflows stay disabled for this purpose ([#157](https://github.com/ChipIn-one/.github/issues/157)). The writer runs only while the frontend registry record says `capabilities.completion: automatic` (since [#217](https://github.com/ChipIn-one/.github/issues/217)); with `manual` (the frontend from [#216](https://github.com/ChipIn-one/.github/issues/216) until #217) the run was skipped before any read, so no FE Issue got `Awaiting release` in that window.
- **Which Issues.** Only results with the decision `awaiting-production`: every linked PR merged into `dev`, none yet contained in a merged `dev -> main` release PR, and all other gates passed. The writer re-verifies every linked PR and the scope-freshness rule itself (`evaluateAwaitingReleaseCandidate`), because the `awaiting-production` code alone is not sufficient (the frontend evaluator stops at the first unreleased PR); a candidate that fails is left unchanged as `awaiting-release-skipped:<code>`. Other decision codes never change Status (the existing `open + Done → In Progress` repair keeps running inside the frontend sweep, unchanged).
- **Transition.** The Project #5 snapshot is read once per run (only when there is a candidate), with the same membership checks as the `Done` repair (`project-membership-missing`, `project-membership-ambiguous`); the item's Status is read fresh. `Todo` or `In Progress` → `Awaiting release`, then read back (a missing or ambiguous `Awaiting release` option stops the run before any write; a read-back mismatch or another per-Issue error is recorded as `awaiting-release-failed: …`, the run continues and exits 1 after the summary). `Awaiting release` → no-op (`awaiting-release-current`), so a rerun writes nothing. `Done`, `Backlog`, any other value or no Status → left untouched (`awaiting-release-skipped:<status>`, `none` for no Status).
- **Stale rule.** Right before the write the Issue is re-read; when it is no longer open (`issue-no-longer-open`) or its `updated_at` differs from the snapshot (`stale-snapshot`) nothing is written and the next run retries.
- **Order with the `Done` repair.** An open `awaiting-production` Issue that still shows derived `Done` is first repaired to `In Progress` by the frontend sweep, then moved to `Awaiting release` in the same run.
- **After the release.** The close (`closed/completed`) happens as before; `Done` stays the derived mirror of the close, so `Awaiting release` turns into `Done` the same way `In Progress` did.
- **Latency.** The Status is written by the `.github` sweep, not by a frontend merge event: it appears at the next sweep run after the merge, which is a push to `.github` `master`, a forwarded frontend Production deployment (`repository_dispatch`, [#228](https://github.com/ChipIn-one/.github/issues/228)) or the throttled schedule (observed every ~5–6 hours), so it can take hours.
- **Receipt.** `awaitingRelease: { enabled, updated: [Issue numbers], skipped: n, failed: [Issue numbers] }` (`skipped` counts every `awaiting-production` Issue left unchanged, including `awaiting-release-current`); the outcome code is appended to the Issue's `decision.detail` and the summary shows `Awaiting release: on (set N, unchanged M, failed K)`.

### `integration-merge` (`.github`, knowledge base)

Every Development-linked PR must be a same-repository PR (`headRepository` is the repository; a merged fork PR gives `ambiguous-development`) merged into `branches.integration`, and its merge commit must still be contained in the current head of that branch (checked with the compare API). A merge commit no longer reachable from the head (force-push, history rewrite) gives `integration-history-diverged`; a failed compare or read gives `integration-evidence-unreadable` for that Issue only.

Sub-issues fail closed: the engine compares the Issue's `sub_issues_summary.total` with the sub-issues it could list; a mismatch (private cross-repository sub-issues hidden from the token) or a missing summary gives `required-relationships-unreadable`.

Scope freshness is stricter than #178. There is no later release: a merge into the integration branch is the terminal evidence, so **any reopen after the last merge counts as a scope change** (`scope-changed-after-implementation`, reason `reopened at …`). The engine never closes a reopened Issue again until a fresh linked PR merges. Checkbox-only body edits are still ignored; a title rename still counts.

**Relationship declaration edits are not a scope change** ([#223](https://github.com/ChipIn-one/.github/issues/223)). The intake (`--relates-to`/`--blocks`/`--parent`) and the relationships reconciler write mirror lines into the *other* Issue's body, often after its PR merged. A body revision whose only difference from the previous revision (after the checkbox normalization) is adding, removing or changing well-formed declaration lines inside the single `## Dependencies` section, outside code fences, is ignored. Grammar (the parser's): optional `- ` or `* ` bullet, a label `Parent:`, `Blocked by:`, `Blocks:` or `Relates to:` matched case-insensitively, whitespace around the line and the target ignored, and exactly one `ChipIn-one/<repo>#<number>` whose repository is in `workflow-registry.yaml` (a ref to another repository is ordinary text). The lines are recognized by the parser of [`relationships.mjs`](../../automation/relationships.mjs) (`stripDeclarationLines`), so the rule follows the relationship grammar. Everything else still counts, byte for byte: any other text or whitespace change in the same revision (including an extra blank line), a declaration-looking line outside `## Dependencies`, a malformed declaration, creating the `## Dependencies` section (the heading is new text), a body with several `## Dependencies` sections (projection ambiguous, fail closed), a title change and every reopen. Because a declaration edit no longer blocks, a `Blocked by:` declared after the merge must not slip through before the reconciler writes the native edge: the shared sweep of `integration-merge` and `deployment-receipt` reads the current body and leaves the Issue open with `relationship-not-reconciled` while a declared `Blocked by:` target has no native blocked-by edge (a target read as closed is ignored, because it would not block even with the edge and the reconciler refuses such edges; an unreadable target counts as open). Once the edge exists the existing `blocked-by-open-issue` gate decides. `Parent:` declarations are not checked this way. The legacy `production-merge` module does not pass the body and has no such gate. The rule lives in the shared policy (`resolveScopeFreshnessFloor` / `isSameScopeText` in `frontend-production-completion-policy.mjs`), so it applies to all three strategies: `integration-merge`, `deployment-receipt` and `production-merge` (#178 rule plus this one exception; `frontend-production-completion.mjs` itself is unchanged).

### `deployment-receipt`

Production evidence is a record the delivery platform writes itself, not a release PR ([#212](https://github.com/ChipIn-one/.github/issues/212); the frontend strategy after its cutover to canonical `master`, [chipin-frontend#497](https://github.com/ChipIn-one/chipin-frontend/issues/497)). The frontend registry record was switched in [#216](https://github.com/ChipIn-one/.github/issues/216) (`completion: deployment-receipt`, `productionEvidence: { environment: Production, creator: "vercel[bot]" }`) with the engine off; [#217](https://github.com/ChipIn-one/.github/issues/217) turned it on (`capabilities.completion: automatic`) after the Promote check below, with `completionRunner: org-sweep`: the org sweep is the only runner, no repository caller.

**Evidence.** A *valid production receipt* is a GitHub Deployment of the repository with:

- `environment` equal to `productionEvidence.environment` and `creator.login` equal to `productionEvidence.creator` (registry, e.g. `Production` / `vercel[bot]`; nothing is hard-coded);
- a full 40-character `sha`;
- a newest status (by `created_at`, then id) with `state: success`, written by the same creator and, when the status names an environment, for the same environment. A later `inactive`, `failure`, `error`, `pending` or `in_progress` status makes the receipt invalid;
- a `sha` on the integration branch: an ancestor of or equal to the current `branches.integration` head. The engine asks `GET /compare/{receiptSha}...{head}` and requires `status: ahead` with `merge_base_commit` = the receipt SHA (equal SHAs need no call). In GitHub's `base...head` compare, `ahead` means the head has commits the base lacks and none the other way round, i.e. the base is an ancestor of the head; `behind` would mean the opposite.

**Close.** Every `integration-merge` gate runs first, unchanged (the same evaluator: native Development link, complete linkage, same-repository PRs, no linked branches, no open blockers, no incomplete or invisible sub-issues, merged into `branches.integration` and still on its head, scope freshness with every reopen after the last merge counted, stale-snapshot check before the close, never reopen). Then **every** linked PR's merge commit must be contained in **some** valid receipt: `GET /compare/{mergeCommit}...{receiptSha}` is `ahead` (or the SHAs are equal). The decision code is `production-receipt-complete`; the summary shows `closed-completed`.

**Awaiting release.** All gates pass but at least one merge commit is in no valid receipt (or there is no valid receipt at all) → `awaiting-production`, never a close. With the writer on, the same writer as for the frontend moves `Todo`/`In Progress` → `Awaiting release` (same membership, stale and read-back rules; `Done`, `Backlog`, other values untouched; an open Issue showing derived `Done` is first repaired to `In Progress`). The re-check before the write (`deploymentReceiptAwaitingVerifier`) re-asserts the layout: open, complete same-repository linkage, every PR merged into `branches.integration`, no linked branches; the evaluator itself already checked every linked PR and the scope rule.

**Evidence in the output.** Each close and `awaiting-production` decision carries `decision.evidence.pullRequests[]`: `number`, `mergeCommitSha`, and `receipt` (`deploymentId`, `sha`, `environment`, `creator`, `createdAt`, `statusId`, `statusState`, `statusCreatedAt`) or `null`; the close diagnostic names the deployment id, SHA and status id/time. The run receipt adds `productionEvidence`: `environment`, `creator`, `deploymentsRead`, `matchingDeployments`, `truncated`, and `checked[]` (every Deployment validated in this run with `valid` and `reason`, e.g. `creator-mismatch`, `newest-status-inactive`, `not-on-integration-branch`); the summary shows one `Production evidence:` line.

**Reads, bounds and failure.**

- Deployments: `GET /deployments?environment=<environment>` newest first, at most 2 pages of 50 (the newest 100). A full window is reported as `truncated`; older Deployments are not evidence (fewer receipts can only keep an Issue open). An unreadable list or a page that is not a list stops the run before any evaluation or write (`PRODUCTION_EVIDENCE_UNREADABLE`, exit 1).
- Receipts are validated lazily, newest first, each at most once per run (one status read per Deployment, one page of 100 statuses; a full page is `statuses-truncated`, invalid, because the newest status cannot be proven); compare results are cached across Issues. When the newest receipt contains everything, older ones are never read.
- A 404 (Deployment or commit gone) makes that receipt invalid. Any other status or compare error while evaluating an Issue leaves that Issue open with `production-evidence-unreadable` (no close, no `Awaiting release`); the sweep continues.
- A record without `productionEvidence` (a registry that bypassed validation) stops the run with `PRODUCTION_EVIDENCE_UNDECLARED` before any read.

**Native auto-close.** After the cutover the integration branch is the default branch, so GitHub's "Auto-close issues with merged linked pull requests" would close Issues at merge, before production, without any gate. It must be disabled in the repository before the first FE PR merges into `master` (with the engine off it would otherwise be the only closer) (same owner action as for `integration-merge`, [above](#native-auto-close-and-the-engine)). Because a reopen after the last merge counts as a scope change, an Issue closed early by GitHub and reopened by a human stays open until a fresh linked PR merges or a human closes it.

**Runner.** The registry field `completionRunner` says who runs the engine: `repository` (default) is a repository caller, required by conformance (`CALLER_MISSING`); `org-sweep` is only an org sweep in `ChipIn-one/.github` that runs `completion.mjs --repository <it>` on a schedule (plus any faster trigger), so no repository caller is required and conformance instead requires that sweep (`COMPLETION_SWEEP_MISSING`, [conformance.md](conformance.md)). `org-sweep` needs `capabilities.completion: automatic`, so switching the engine off means `capabilities.completion: manual` and dropping `completionRunner` together. `chipin-frontend` uses `org-sweep` (owner decision 2026-10-22): its sweep is [`.github/workflows/frontend-production-completion.yml`](../../.github/workflows/frontend-production-completion.yml), latency within minutes of the Promote when chipin-frontend forwards the Production deployment as `repository_dispatch` ([chipin-frontend#559](https://github.com/ChipIn-one/chipin-frontend/issues/559)), otherwise at the next push to `.github` `master` or the next schedule run, which GitHub throttles (observed every ~5–6 hours, [#228](https://github.com/ChipIn-one/.github/issues/228)). A repository that wants an immediate close may still add the caller below; when it exists, its triggers are checked.

**Triggers.** The repository caller ([`templates/caller-completion-deployment-receipt.yml`](../../templates/caller-completion-deployment-receipt.yml)) runs the composite action on:

- `deployment_status`, only when `github.event.deployment_status.state == 'success'` and `github.event.deployment.environment` is the registry environment (filtered in the job `if:`; the engine validates the receipt again);
- `push` to the integration branch, so `Awaiting release` appears right after the merge;
- `workflow_dispatch`, a manual rerun (the engine takes no input);
- the org sweep as the fallback for missed events: [`.github/workflows/frontend-production-completion.yml`](../../.github/workflows/frontend-production-completion.yml) runs `completion.mjs --repository ChipIn-one/chipin-frontend` on `.github` pushes, on the frontend Production dispatch and on a throttled schedule (observed every ~5–6 hours) with the org write PAT, `CHIPIN_COMPLETION_AWAITING_RELEASE=1` and `CHIPIN_COMPLETION_SKIP_MANUAL=1`; it follows the registry strategy and is a green no-op if the record says `capabilities.completion: manual`. For `chipin-frontend` (`completionRunner: org-sweep`) it is not a fallback but the only runner.

With `awaiting-release: "true"` the caller's `token` is the org PAT `CHIPIN_ISSUE_WRITE_TOKEN` (made available to the repository by the owner); for that repository it needs Deployments read, Issues write and Project #5 read/write, and the workflow's own `permissions` stay `contents: read`. The `GITHUB_TOKEN` scopes (`deployments: read`, `issues: write`, `pull-requests: read`) matter only for the variant with `token: github.token` and `awaiting-release: "false"`: the close still works, `Awaiting release` then comes from the org sweep. A `deployment_status` run uses the workflow file at the deployment's SHA, so receipts for commits made before the caller existed start no run; the org sweep covers them. Conformance checks that the `completion-action` caller, when there is one, has the `deployment_status` and `push` triggers (`COMPLETION_TRIGGER_MISSING`, [conformance.md](conformance.md)).

**Token precondition for the frontend.** The PAT used by the org sweep (`.github/workflows/frontend-production-completion.yml`, `CHIPIN_ISSUE_WRITE_TOKEN`) must have Deployments: read on `chipin-frontend`; otherwise every run stops with `PRODUCTION_EVIDENCE_UNREADABLE` (nothing is closed, no `Awaiting release`, red run). The first sweep after [#217](https://github.com/ChipIn-one/.github/issues/217) shows it.

**Promote evidence (cutover plan step 7, verified 2026-10-22, [#217](https://github.com/ChipIn-one/.github/issues/217#issuecomment-6343177957), plan [chipin-frontend#497](https://github.com/ChipIn-one/chipin-frontend/issues/497#issuecomment-6339879917)).** Vercel builds every `master` push as **Preview** only: the merge of chipin-frontend#502 (`e6d2f2e`) became Deployment `7254446063`, environment `Preview`; neither that build nor a UI Redeploy of it created a `Production` record. Only **Promote to Production** of that deployment made Vercel rebuild the commit with the production env and write Deployment `7254813070`: environment `Production`, creator `vercel[bot]`, sha `e6d2f2e1aa34e99ccc20cd299137ce2e0070e342`, status `success` (`20269730921`) by `vercel[bot]`. So the `Production` / `success` record exists only after a Promote and is valid evidence. The Vercel production branch stays `main` (Vercel rejects a branch that does not exist) with `vercel.json` `git.deploymentEnabled.main: false`, so no push creates a production build; `main` is frozen as a rollback ref. **Emergency switch-off** (e.g. if Vercel ever writes `Production` at build time): in the frontend record set `capabilities.completion: manual` **and** drop `completionRunner: org-sweep` in the same change (validation rejects `org-sweep` with `manual`); the org sweep then returns a green `skipped` receipt (`CHIPIN_COMPLETION_SKIP_MANUAL=1`) until a corrected evidence source is agreed.

### `manual`

No automation. With `capabilities.completion: manual` the engine refuses to run (`COMPLETION_NOT_AUTOMATIC`, exit 1). An org sweep that sets `CHIPIN_COMPLETION_SKIP_MANUAL=1` gets a `skipped` receipt instead (exit 0, no GitHub read or write); only a record with `capabilities.completion: manual` is skipped, every other refusal still fails the run. The capability can be `manual` while the top-level `completion` names a strategy (the frontend between [#216](https://github.com/ChipIn-one/.github/issues/216) and [#217](https://github.com/ChipIn-one/.github/issues/217)). The frontend org sweep keeps `CHIPIN_COMPLETION_SKIP_MANUAL=1` after #217: harmless while the record is automatic.

## When the engine leaves an Issue open

`integration-complete` and `production-receipt-complete` are the internal decision codes; the summary and receipt show `closed-completed` once the close succeeds.

| Code | Meaning | What a human does |
| --- | --- | --- |
| `closed-completed` | The Issue was closed as completed by the engine. | Nothing. |
| `already-closed` | The Issue is closed (manual or native close is preserved). | Nothing; reopen by hand if the close was wrong. |
| `required-relationships-unreadable` | Sub-issues or `blocked by` could not be read, or `sub_issues_summary` is missing or does not match the listed sub-issues. | Check token permissions; the next run retries. |
| `required-sub-issue-incomplete` | A native sub-issue is not `closed/completed`. | Finish or close the sub-issue. |
| `blocked-by-open-issue` | A native blocker is still open. | Resolve the blocker or remove the relationship. |
| `relationship-not-reconciled` | `## Dependencies` declares a `Blocked by:` target (open or unreadable) without a native blocked-by edge (#223; `integration-merge`, `deployment-receipt`). | Wait for the relationships reconciler (`*/30`) or fix the declaration; a reconciler `BLOCKED` comment names the cause. |
| `development-branch-pending` | Development lists linked branches. | Open a PR for the work or unlink the branch. |
| `missing-development` | No native Development-linked PR. | Link the PR in Development (`Task identity:` line + development-link caller, or by hand in the PR sidebar). |
| `ambiguous-development` | Incomplete pagination, duplicate, cross-repository or fork PR, unsupported base. | Fix the links; cross-repository work is closed by hand. |
| `implementation-not-merged` | A linked PR is not merged or its merge commit is unreadable. | Merge or unlink the PR. |
| `awaiting-production` | `production-merge`: merged to `dev`, not yet in a merged release PR. `deployment-receipt`: merged into the integration branch, not yet in a valid production receipt (or none exists). With the writer on, Project Status moves to `Awaiting release` (outcome appended to the diagnostic). | Merge the `dev -> main` release PR / promote a deployment that contains the merge. |
| `production-evidence-unreadable` | `deployment-receipt` only: a Deployment status or compare read failed for this Issue (not a 404); the Issue is skipped, the sweep continues, no `Awaiting release`. | Nothing; the next run retries. |
| `ambiguous-production` | FE only: release evidence cannot be resolved unambiguously. | Inspect the release PR; close by hand if justified. |
| `integration-history-diverged` | `integration-merge` only: merge commit not in the branch head. | Decide by hand whether the work still ships. |
| `integration-evidence-unreadable` | `integration-merge` only: the compare or a read failed for this Issue; the Issue is skipped, the sweep continues. | Nothing; the next run retries. |
| `scope-history-unreadable` | Timeline or body edit history incomplete or unreadable. | Check token scope; close by hand if justified. |
| `scope-changed-after-implementation` | Reopen, body text edit or title change after the last merge. Checkbox-only edits and relationship-declaration-only edits in `## Dependencies` (#223) are ignored and a rename always counts; FE (#178) also ignores a reopen undoing an early manual close, `integration-merge` counts every reopen. | Link and merge a fresh implementation PR, or close by hand. |
| `stale-snapshot` | The Issue changed between evaluation and close. | Nothing; the next run re-evaluates. |

## Engine

```bash
CHIPIN_COMPLETION_WRITE=1 CHIPIN_CANONICAL_WRITE_TOKEN=<token> [CHIPIN_COMPLETION_PROJECT_RECONCILE=0] [CHIPIN_COMPLETION_AWAITING_RELEASE=1] [CHIPIN_COMPLETION_SKIP_MANUAL=1] \
  node automation/completion.mjs --repository ChipIn-one/<repo> [--output receipt.json]
```

- `CHIPIN_COMPLETION_WRITE=1` and a token are mandatory; `--repository` falls back to `GITHUB_REPOSITORY`.
- `CHIPIN_COMPLETION_PROJECT_RECONCILE=0` disables Project #5 reads and writes. Repository-local runs always set it, because a repository `GITHUB_TOKEN` cannot read org Projects; the org-PAT runs (frontend fallback and `.github`) keep the `open + Done` repair.
- `CHIPIN_COMPLETION_AWAITING_RELEASE=1` turns on the `Awaiting release` writer; it has an effect only for `production-merge` and `deployment-receipt` with Project reconciliation on (the frontend org fallback sets it; `.github` does not; the composite action only with its input `awaiting-release: "true"`).
- `CHIPIN_COMPLETION_SKIP_MANUAL=1` (org sweeps only; the frontend org sweep sets it, no effect while its record is automatic): a record with `capabilities.completion: manual` returns a receipt with `skipped: { code: COMPLETION_NOT_AUTOMATIC, detail }` and empty `results` before any GitHub read, and the run exits 0. Repository-local callers and `.github` never set it, so a manual record there stays a red run.
- Receipt (`--output`): `contract: chipin-completion/v1`, `repository`, `strategy`, `branch`, `projectNumber`, `projectReconciliation`, `awaitingRelease` (`enabled`, `updated`, `skipped`), `deployment-receipt` only: `productionEvidence` ([above](#deployment-receipt)), `results[]` (`issue`, `decision.action` / `code` / `detail`, `deployment-receipt` also `decision.evidence`). The Markdown summary goes to stdout and to the step summary.
- A blocked run (`COMPLETION_NOT_AUTOMATIC`, `STRATEGY_NOT_IMPLEMENTED`, `STRATEGY_BRANCH_MISMATCH`, `PRODUCTION_EVIDENCE_UNDECLARED`, `PRODUCTION_EVIDENCE_UNREADABLE`, unreadable branch head, API failure) exits 1. Issues left open are a normal result.

### In Progress at Development link

[#218](https://github.com/ChipIn-one/.github/issues/218): the board shows started work without a manual move, so the completion engine later finds `In Progress` (it moves only `Todo`/`In Progress` to `Awaiting release`).

- **Writer.** `setInProgressAfterLink` in [`development-link.mjs`](../../automation/development-link.mjs), run by the same reconciler right after the native Development link is confirmed (new link read back, or `already-linked`). Never before the link, never without its read-back.
- **Transition.** Project #5 Status `Backlog` or `Todo` → `In Progress`. `In Progress` → no-op (`in-progress-current`); `Awaiting release`, `Done`, empty and any other value → left as it is (`in-progress-skipped:<status>`, `none` for empty). Never backwards.
- **Eligibility.** The PR is open, not a draft, same-repository (head and base), into the registry integration branch, not opened by `dependabot[bot]`, and its body still carries exactly one `Task identity:` line naming the linked Issue (a PR without the line is accepted only when the dispatch input named the identity); the Issue is open and is an Issue. Anything else is a no-op (`pr-not-open`, `pr-draft`, `pr-not-same-repository`, `pr-not-integration-branch`, `pr-task-identity-changed`, `dependabot-pr`, `issue-not-open`) without a Project read; `pr-not-integration-branch` and `pr-task-identity-changed` mean drift since the link and are warnings. A draft PR is parked work; the move happens on the `ready_for_review` event. To park work, close the PR or convert it to draft, or unlink it; the writer never moves a Status back, so set the Status by hand when parking an Issue that is already `In Progress`.
- **Safeguards.** Cheap path first: the Issue's own `projectItems` must show exactly one Project #5 item; when its Status is not `Backlog`/`Todo` the writer stops there, without reading the whole Project. Only on the write path is the Project read with `readProjectSnapshot` (the [#221](https://github.com/ChipIn-one/.github/issues/221) phantom-page reader), whose listing must show the same single item and gives the mutation coordinates; missing, duplicate or divergent membership, an unreadable Project or a missing `In Progress` option is `blocked`. Right before the mutation the PR/Issue eligibility is read again first and the item Status last (the Status field name comes from `config.project.statusField`): a PR or Issue closed or drafted meanwhile gives its no-op code, a Status changed since the snapshot (for example to `Awaiting release`) gives `stale-snapshot` and nothing is written. After the mutation the Status is read back, with one short retry; a mismatch or an unreadable read-back is `PROJECT_STATUS_READBACK`. Any error after a successful mutation carries `mutated: true` (`null` when the mutation answered with an unexpected item, so whether it applied is unknown); the receipt never says `mutated: false` after a write. Then the PR and the Issue state are read once more; one no longer open (or unreadable) is flagged as `prStateAfterWrite` / `issueStateAfterWrite` in the receipt (warning, never reverted).
- **Fail closed without losing the link or the check.** The receipt keeps the link result (`result`, `readBackConfirmed`) and adds `projectStatus` (`result: updated | unchanged | blocked`, `code`, `detail`). Deterministic faults fail the job after the link (exit 1, `::error::`): a broken write path (`PROJECT_STATUS_WRITE`, `PROJECT_STATUS_READBACK`, `PROJECT_STATUS_FIELD` for a missing Status field or `In Progress` option), no access to Project #5 (`PROJECT_ACCESS`: the Project is null/unavailable or the token is denied), a broken configuration (`PROJECT_CONFIG`, `OPT_IN_MISCONFIGURED`) and an unexpected exception (`PROJECT_STATUS_ERROR`). Transient or drifted outcomes (`PROJECT_UNREADABLE` for phantom pages, the read deadline and other transient read failures, `PROJECT_ITEM_UNREADABLE`, `ISSUE_OR_PR_UNREADABLE`, membership problems, `stale-snapshot`, `pr-not-integration-branch`, `pr-task-identity-changed`, `prStateAfterWrite`, `issueStateAfterWrite`) are a `::warning::` with exit 0, so the PR check stays green; the next PR event retries, because the link is then `already-linked`. A misconfigured opt-in (`set-in-progress` other than exactly `true`/`false`, or `true` with an empty `project-status-token`) never blocks the link: the link runs as usual, the Status move is skipped and `OPT_IN_MISCONFIGURED` is reported as an error afterwards.
- **Token and opt-in.** The callers' `token` is the repository `github.token`, which cannot write an org Project, and `admission-token` is the read-only `CHIPIN_DEV_READ_TOKEN`. So the writer is an explicit action input: `set-in-progress` (default `"false"`: no Project read or write) plus `project-status-token`, an org token that reads and writes Project #5 (`CHIPIN_ISSUE_WRITE_TOKEN`). The admission step computes the flag once in bash with an exact, case-sensitive match (`true`, `false`, otherwise `invalid`) and passes it as a step output; the reconcile step reads only that output and is the only step that receives the token. The caller's own `permissions` do not change.
- **Who has it.** No caller yet. The `.github` caller ([`.github/workflows/native-development-link.yml`](../../.github/workflows/native-development-link.yml)) is enabled in the follow-up pin-bump PR: pin to the first org tag that contains #218, plus `set-in-progress: 'true'` and `project-status-token: ${{ secrets.CHIPIN_ISSUE_WRITE_TOKEN }}` (the PAT org workflows already use). The frontend, backend and knowledge-base callers keep the default (off).
- **Enabling another repository (owner configuration).** 1) Decide to expose the org write PAT to that repository's Actions (today only org workflows hold it; the frontend Project writer [`pr-project-writer.mjs`](../../automation/pr-project-writer.mjs) deliberately keeps it out of the frontend repository), and make the org secret `CHIPIN_ISSUE_WRITE_TOKEN` visible to it. 2) In that repository's `native-development-link.yml`, bump the `development-link-action` pin to a tag with #218, make sure the `pull_request` types include `ready_for_review` (a draft PR moves only when it becomes ready), and add `set-in-progress: 'true'` and `project-status-token: ${{ secrets.CHIPIN_ISSUE_WRITE_TOKEN }}`. Until then their Issues move to `In Progress` by hand.

### Token and visibility

The engine sees only what its token sees. Hidden sub-issues are caught by the `sub_issues_summary` check, but blockers in repositories the token cannot read are **not** detectable: the `blocked by` list simply omits them. The org PAT sees private BE and KB blockers and sub-issues. A repository token sees only its own repository, so a KB Issue blocked only by a private BE Issue could be closed; the owner may later supply an org read token to the KB caller (future option, not part of #179).

Paths:

- Composite action [`automation/completion-action`](../../automation/completion-action/action.yml): input `token` (repository token with `issues: write`), Project repair off. Optional input `awaiting-release` (`"false"` by default; `"true"` turns on Project reconciliation and the `Awaiting release` writer and then needs an organization token that reads and writes Project #5; any other value fails the step).
- Org workflow [`.github/workflows/integration-completion.yml`](../../.github/workflows/integration-completion.yml): `.github` itself, push to `master` and schedule, no `workflow_dispatch`. It passes the org write PAT `CHIPIN_ISSUE_WRITE_TOKEN` as `CHIPIN_CANONICAL_WRITE_TOKEN`, like the frontend fallback, so it sees private BE/KB blockers and sub-issues and keeps Project #5 reconciliation on; the workflow's own `permissions` are `contents: read` only.
- Org workflow [`.github/workflows/frontend-production-completion.yml`](../../.github/workflows/frontend-production-completion.yml): the only frontend runner (`completionRunner: org-sweep`, [#217](https://github.com/ChipIn-one/.github/issues/217)), push to `master`, `repository_dispatch` `frontend-production-deployed` (sent by chipin-frontend's `forward-production-deployment.yml` on a successful `vercel[bot]` Production deployment, [#228](https://github.com/ChipIn-one/.github/issues/228); the payload is a hint only and is never read, the engine re-reads the receipt, so a forged dispatch only starts an ordinary run) and the schedule as the fallback (GitHub throttles it, observed every ~5–6 hours), no `workflow_dispatch`, org write PAT as `CHIPIN_CANONICAL_WRITE_TOKEN`; runs `completion.mjs --repository ChipIn-one/chipin-frontend` with `CHIPIN_COMPLETION_AWAITING_RELEASE=1`, `CHIPIN_COMPLETION_SKIP_MANUAL=1` (no effect while the record is automatic) and Project #5 reconciliation on.
- Template [`templates/caller-completion-integration.yml`](../../templates/caller-completion-integration.yml): KB-like callers, the action pinned to an org tag SHA, repository token (`github.token`, limitation above). KB already has its development-link caller.
- Template [`templates/caller-completion-deployment-receipt.yml`](../../templates/caller-completion-deployment-receipt.yml): `deployment-receipt` callers (`deployment_status` success in the registry environment, push to the integration branch, `workflow_dispatch`), org PAT and `awaiting-release: "true"`, workflow `permissions: contents: read` ([above](#deployment-receipt)).
- [`development-link.mjs`](../../automation/development-link.mjs) accepts `meta` repositories since `v1.3.0`, so `Task identity: ChipIn-one/.github#N` parses; [`.github/workflows/native-development-link.yml`](../../.github/workflows/native-development-link.yml) is the `.github` caller (same shape as the frontend and knowledge-base callers, `workflow_dispatch` with the exact head SHA for a PR opened before the caller existed).
