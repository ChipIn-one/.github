# Conformance audit

Checks that a repository matches its record in [`workflow-registry.yaml`](../../workflow-registry.yaml). Specified by the
[ChipIn Workflow Standard v1](README.md#6-conformance-audit); implemented by [#154](https://github.com/ChipIn-one/.github/issues/154) in `automation/conformance.mjs`
and `.github/workflows/conformance-audit.yml`.

```bash
# read-only audit of everything (or --repository owner/name); writes artifacts, never Issues
GITHUB_TOKEN=... node automation/conformance.mjs audit --dir conformance --output conformance-report.json --summary conformance-summary.md
# plan, then apply, the drift Issues (apply needs --activate conformance-v1 and CHIPIN_CONFORMANCE_WRITE=1)
GITHUB_TOKEN=... node automation/conformance.mjs upsert --report conformance-report.json
```

## Result and severity

Per repository `conformance-<repo>.json` (`.github` is `conformance-dot-github.json`) plus the combined report and a job summary. Status: `CONFORMANT`, `DRIFT` (at least one `drift` finding) or
`UNREADABLE` (a read failed; the audit job fails, nothing is opened, edited or closed for that repository). Findings are either `drift` (counts, drives the Issue) or `note` (reported only).
Organization repositories that are not in the registry are listed once as `UNREGISTERED` in the summary (full runs only); no action is taken.

Repositories are audited on their **integration branch** (`branches.integration`). Meta repositories (`kind: meta`) host the shared actions, so the caller checks do not apply to them until they adopt `pr-gate` (#153).

`chipin-frontend` is audited on canonical `master` since [#216](https://github.com/ChipIn-one/.github/issues/216) (default = integration = `master`, no promotion branch): `requiredChecks: [frontend-ci]` must be enforced by the ruleset on `master`, Dependabot `github-actions` must target `master` (or the default branch), and `AGENTS.md` is read from `master` (its workspace record declares no `contextPath` since [#252](https://github.com/ChipIn-one/.github/issues/252)). Its record says `completion: deployment-receipt`, `capabilities.completion: automatic` and `completionRunner: org-sweep` since [#217](https://github.com/ChipIn-one/.github/issues/217) (owner decision: no FE completion caller), so `CALLER_MISSING` does not require a completion caller; instead `COMPLETION_SWEEP_MISSING` requires the org sweep `.github/workflows/frontend-production-completion.yml` to keep running `completion.mjs --repository ChipIn-one/chipin-frontend` on a schedule. If a `completion-action` caller is added anyway (immediate close), `COMPLETION_TRIGGER_MISSING` checks its triggers. A leftover `frontend-production-completion-action` caller is not a finding (the audit only checks required callers); it is removed in the frontend cutover ([chipin-frontend#497](https://github.com/ChipIn-one/chipin-frontend/issues/497)).

The release flow is checked against the registry `release` block ([release.md](release.md), [#174](https://github.com/ChipIn-one/.github/issues/174)) for every kind, `meta` included: a strategy other than `none` needs a workflow that uses the reusable `ChipIn-one/.github/.github/workflows/release.yml` (for `.github` that is `.github/workflows/release-on-master.yml`) from a workflow whose trigger matches the registry trigger (`push` for `integration-merge`/`promotion-merge`; `deployment_status`, `workflow_run` or `workflow_dispatch` for `production-deploy`), the newest `<tagPrefix>X.Y.Z` tag must be on the history of the release branch (`branches.promotion` for `promotion-merge`, otherwise `branches.integration`), and each of the newest 5 tags needs a published GitHub Release. For `deploy-tag` the branch check is stricter than the engine, which takes the deployed SHA as is: conformance still requires the newest tag on the history of the integration branch. A compare that returns 404 (orphan tag commit, missing branch) is `RELEASE_TAG_OFF_BRANCH`, not `UNREADABLE`. Tags and Releases are read the way the release engine reads them (`githubStore` of `automation/release.mjs`); a failed read makes the repository `UNREADABLE`. Not checked yet: that the latest production state carries a tag or an explained "no new version" (needs the deployed SHA and an engine plan), and that task PRs no longer change the version in the frontend (after the old-flow cleanup [#172](https://github.com/ChipIn-one/.github/issues/172)).

The routing checks are a **drift detector, not a security control**. They compare the managed block and look for a few known bad patterns; they do not prove that an `AGENTS.md` is safe. Text outside the managed block is protected only by review in the consumer repository.

## Early close guard

`CLOSED_BEFORE_PRODUCTION` ([#181](https://github.com/ChipIn-one/.github/issues/181)) makes a manual close before production visible: the completion engine never touches a closed Issue, so such a close silently takes the Issue out of completion. The check is read-only and a `note` (count and list only, no drift Issue): conformance never reopens, edits, relabels or comments on the Issue, and the finding clears by itself after the Promote that contains the merge.

- **Remediation**: leave the Issue closed. Reopen it only if the work is really not done: a reopen after the merge is a scope change for the engine (`evaluateIssueForIntegrationCompletion`, [completion.md](completion.md)), so the Issue stays open until a fresh linked PR merges or a human closes it. Close Issues by hand only after production.
- **Scope**: records with `completion: deployment-receipt` or `production-merge` (not `meta`). `integration-merge` and `manual` records are not checked.
- **Bound**: Issues closed in the last 30 days (`CLOSED_BEFORE_PRODUCTION_DAYS`), read newest-updated first (`filterBy.since`) in at most 4 pages of 50 (`CLOSED_SCAN_MAX_PAGES`, `CLOSED_SCAN_PAGE_SIZE`); a fuller window is the note `CLOSED_BEFORE_PRODUCTION_WINDOW_FULL`. Only `state_reason: completed` closes count; a PR counts when its base and head repository are the audited repository (fork PRs are skipped, as in the engine), it is merged into `branches.integration` and its merge commit is readable. Development linkage is read up to 50 PRs per Issue; a partial list fails closed (`UNREADABLE`) only for a candidate (completed, in the window, not an engine close).
- **Engine closes**: closes by `github-actions` (repository callers) are skipped. The org sweep closes with `CHIPIN_ISSUE_WRITE_TOKEN`, a personal token that acts as its owner, so its closes cannot be told apart by actor; they need no exclusion, because the engine closes only after production evidence contains every merge commit, so an engine close is never "not yet in production".
- **Keyword closes**: on a repository whose integration branch is the default branch (FE `master`), a `Closes #N` keyword in the PR closes the Issue at merge, before the production receipt. Such a close is not an engine close, so it is reported once, marked `via the closing keyword of PR #N` (from `ClosedEvent.closer`), and clears after the receipt that contains the merge.
- **Evidence**: read lazily, only when a candidate exists, with the engine's own readers. `deployment-receipt`: `readProductionDeployments`, `createReceiptResolver` and `readBranchHead` of `automation/completion.mjs` with `compareContainsCommit`: the newest 100 Deployments of the `productionEvidence` environment, each validated as a receipt (newest status `success` by the creator, SHA on the integration branch). `production-merge`: `readProductionReleases` of `automation/frontend-production-completion.mjs`: the head SHA of a merged `dev` -> `main` release PR, merged at or after the PR, must contain the merge commit (not the `main` head: release PRs may be squashed); another branch layout is the note `CLOSED_BEFORE_PRODUCTION_SKIPPED`. A 403 on the evidence read or a receipt window without a single valid receipt is the note `CLOSED_BEFORE_PRODUCTION_UNVERIFIABLE`, so this note-level check never makes the repository `UNREADABLE` or hides its drift for a missing permission. Any other read error (5xx, malformed answers, a failed closed-Issue scan, a missing pagination cursor, incomplete linkage of a candidate) fails closed: the repository is `UNREADABLE`, never clean. The audit token needs `Deployments: Read-only` in addition to contents, pull requests and Issues.
- **Comment on the Issue**: the per-Issue explanatory comment of [#181](https://github.com/ChipIn-one/.github/issues/181) is moved to the follow-up Issue. No existing writer of conformance writes to product Issues (`upsert` writes only drift Issues in `ChipIn-one/.github`), and the completion engine is the only writer of product Issues; the follow-up decides which writer owns it.

## Drift Issues

One Issue per non-conformant repository in `ChipIn-one/.github`: first line `Conformance: ChipIn-one/<repo>`, Type Task, assignee = the registry owner (a `docs` repository without an owner falls back to the owner of the
`.github` record), Priority P2, Project #5 Status `Backlog`, no labels, body with `## Problem`, `## Outcome` and one `## Acceptance` checkbox per finding. A rerun with the same findings changes nothing
(the audit time alone never rewrites the Issue); changed findings update the body; at zero drift the Issue is closed as completed and its Project Status is set to `Done` (the derived mirror). A new drift
episode after closure creates a new Issue; a second open Issue with the same marker is reported as a duplicate and never created.

## Rollout

Scheduled runs (Mondays 05:17 UTC) audit and only print the planned Issue actions until the repository variable `CONFORMANCE_AUDIT_APPLY` is `true`; a dispatch applies only with `apply=true`.
The audit reads other repositories with `CHIPIN_DEV_READ_TOKEN` (contents, Issues and pull requests, rules, protection, checks, Project #5, and `Deployments: Read-only` on `deployment-receipt` repositories for `CLOSED_BEFORE_PRODUCTION`; without it that check is the note `CLOSED_BEFORE_PRODUCTION_UNVERIFIABLE`); a repository the token cannot read is `UNREADABLE`, never silently conformant.
Writes use the separate `CHIPIN_ISSUE_WRITE_TOKEN`.
