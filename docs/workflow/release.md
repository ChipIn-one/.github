# Release policy

Native tags and GitHub Releases for ChipIn repositories. Owner decisions of 2026-10-21 (epic [#167](https://github.com/ChipIn-one/.github/issues/167)); the per-repository rule lives in the
`release` block of [`workflow-registry.yaml`](../../workflow-registry.yaml). This page is the policy; the automation lands task by task (Rollout below) and is active only where a caller exists (`.github` since #175).

## Rules

1. **The version is a git tag** `vX.Y.Z` (prefix from `release.tagPrefix`, default `v`) plus a native GitHub Release. No task changes a version; `package.json` does not carry the release version.
2. **The increment comes from `## Version impact`** of the PRs included since the previous tag: the maximum of `major` > `minor` > `patch` > `none`. A missing or invalid value blocks the release (no guessing) and keeps blocking every later run until the merged PR body is fixed and the run repeated, or a tag is placed by hand ([README §4](README.md#4-versioning-and-pins)). The one exception: a PR authored by `dependabot[bot]` whose body has no `## Version impact` section gets a default from its head branch `dependabot/<ecosystem>/…`: `github_actions` counts as `none` (an action pin bump changes nothing a consumer pins), any other ecosystem (`npm_and_yarn`, `pip`, `docker`, …) counts as `patch` (a runtime dependency bump ships code to production and needs a version); a head branch that cannot be read or does not start with `dependabot/` still blocks, and an explicit section in its body always wins. `major` from 0.x is rejected: `1.0.0` is an explicit owner decision.
3. **All `none` means no new version:** no tag and no Release are created; the change ships as part of the previous version.
4. **Only a human merges.** Tags and Releases are created automatically *after* a human merge (or a successful production deploy), never before, and never by merging.
5. **Release notes are generated:** native GitHub generated notes from the merged PRs plus an "Included Issues" block built from the inventory (`Task identity` of the included PRs). Nothing is written by hand.
6. **Sentry** gets a release only for a tag build (frontend: the tagged Production redeploy, [Frontend specifics](#frontend-specifics)); dev and preview builds get no separate Sentry release.
7. **Unchanged:** `Version impact` stays in every task PR; Milestones stay product goals and are not versions. Completion is separate from releases: on canonical `master` FE Issues close on a production Deployment receipt, written by Vercel at Promote; the org sweep runs the engine since [#217](https://github.com/ChipIn-one/.github/issues/217), within minutes of a Promote via the frontend Production dispatch ([#228](https://github.com/ChipIn-one/.github/issues/228)), otherwise on a throttled schedule observed every ~5–6 hours ([completion.md](completion.md#deployment-receipt)).

Registry rules: `none` has no trigger; `semver-by-impact` uses `promotion-merge` (needs `branches.promotion`) or `integration-merge`; `deploy-tag` uses `production-deploy` (needs `deploymentProfile: production`); `tagPrefix` is 0-8 lowercase letters.

## Frontend specifics

- **Canonical `master`** ([chipin-frontend#497](https://github.com/ChipIn-one/chipin-frontend/issues/497), approved plan; registry switch [#216](https://github.com/ChipIn-one/.github/issues/216)): there is no `dev -> main` release PR any more; the owner releases by promoting an exact `master` deployment in Vercel. The registry record is `release: { strategy: deploy-tag, trigger: production-deploy, tagPrefix: v }`, so the tag belongs to the promoted (deployed) SHA, like the backend. The switch came in the cutover window together with `completion: deployment-receipt` (engine on since [#217](https://github.com/ChipIn-one/.github/issues/217), run by the org sweep); tags are independent of the completion strategy ([#212](https://github.com/ChipIn-one/.github/issues/212)).
- **Caller** `.github/workflows/release-on-production.yml` ([chipin-frontend#586](https://github.com/ChipIn-one/chipin-frontend/issues/586)): on a successful `deployment_status` of the `Production` environment created by `vercel[bot]`, a guard job checks that the deployed SHA is on `master` and is not a rollback behind the newest tag (a rollback creates no tag), serialised with the release by a `concurrency` group; then the reusable release workflow runs with `apply: true` on the deployed SHA.
- Admission, the Development link and `pr-metadata` route FE PRs from the registry: an implementation PR is any same-repository branch into `master`; PRs into `dev` or `main` are rejected (`Unsupported PR branch transition`, `ROUTE: only implementation→master`). The `dev -> main` release-PR path (inventory format `Included implementation PRs:` / `Included Issues:`) stays in the code only for the rollback record of the cutover window (`semver-by-impact` / `promotion-merge` with `branches.promotion: main`); `templates/caller-release-promotion.yml` has no registered user now.
- **Tagged Production redeploy** ([#187](https://github.com/ChipIn-one/.github/issues/187), [#172](https://github.com/ChipIn-one/.github/issues/172), [chipin-frontend#680](https://github.com/ChipIn-one/chipin-frontend/issues/680)): Promote to Production is a full Vercel rebuild of the promoted commit, and the tag is created only after that build succeeds (v1.1.1: build 08:54, tag 08:55 UTC), so the promoted build cannot know its version. After the engine returns `RELEASED`, a `redeploy` job in the caller asks the Vercel API to redeploy that same Production deployment (same commit, `target: production`). Its own `deployment_status` reaches the engine as `ALREADY_RELEASED`, so there is no loop. If Production has moved to another deployment since the Promote (a newer Promote or a rollback), the job skips with a warning; a Promote made while the redeploy builds is overwritten when it finishes (Promote again). The job needs the FE secret `VERCEL_TOKEN` and the variables `VERCEL_TEAM_ID` and `VERCEL_PROJECT_ID`; a failure is a red job, and the owner redeploys by hand in Vercel.
- Builds: the build looks up `vX.Y.Z` tags on its own commit (on Vercel with `git ls-remote --tags` of the public repository, elsewhere with local tags). A tag on the commit gives `X.Y.Z` in the app and the Sentry release; every other build, including the first pre-tag Production build, is `<last tag>-dev-<sha7>` (`0.0.0-dev-<sha7>` without tags) and creates no Sentry release. A failed lookup labels the build untagged, never as a release.
- The old flow (`version:bump`, `version:check`, the `package.json` base version, the related rules) is removed by [#172](https://github.com/ChipIn-one/.github/issues/172); `package.json` keeps a frozen `version` that nothing reads.
- Tags: historical versions `v1.0.2`-`v1.0.8` were backfilled on the matching `main` merge commits ([#171](https://github.com/ChipIn-one/.github/issues/171)); `v1.0.10` was placed by hand on 2026-11-03 on the then-Production SHA to match `package.json`.

## Engine (`automation/release.mjs`, task #169)

One engine for every `semver-by-impact` and `deploy-tag` repository; the registry profile decides the release branch and the tag prefix.

```bash
# read-only plan (prints the decision, writes nothing)
node automation/release.mjs plan --repository ChipIn-one/.github --ref master [--output receipt.json]
# apply: explicit activation and env switch; the token needs contents: write on the repository
CHIPIN_RELEASE_WRITE=1 node automation/release.mjs apply --repository ChipIn-one/.github --ref <sha> --activate release-v1
```

Steps, all fail-closed:

1. Resolve `--ref` to a commit. For `promotion-merge` it must be contained in `branches.promotion`, for `integration-merge` in `branches.integration` (`COMMIT_NOT_ON_RELEASE_BRANCH` otherwise); `production-deploy` takes the deployed SHA as is.
2. Previous tag: the highest `<prefix>X.Y.Z` tag that is an ancestor of the commit. Tags on other branches are skipped; if tags exist but none is an ancestor → `PREVIOUS_TAG_UNREACHABLE`. A repository without tags needs `--initial-version X.Y.Z` (`NO_PREVIOUS_TAG`); that first release has no inventory and the flag is rejected once a tag exists.
3. Inventory: the commits between the previous tag and the release commit; for each, the merged pull requests whose base is `branches.integration` and whose merge commit is in that range (for the frontend on canonical `master` these are the implementation PRs merged into `master`). With a promotion record (the frontend `dev -> main` rollback record), PRs merged into the promotion branch (the release PR itself, a hotfix straight into `main`) are never counted and are reported as `excludedPullRequests`; commits covered by neither (direct pushes) are `unattributedCommits` and carry no impact. Commits in the range but **no** included PR (a squash-merged promotion, a hotfix-only range, direct pushes only) → `NO_INCLUDED_PULL_REQUESTS`: nothing is guessed, a human decides.
4. Impact: the first non-empty line of `## Version impact` of every included PR must start with `none`, `patch`, `minor` or `major` (list markers, backticks and bold are ignored, so "- `patch`: …" and "Patch: …" parse). A missing section or any other text → `INVALID_VERSION_IMPACT` with the offending PRs; nothing is guessed. Only a missing section on a PR whose author login is `dependabot[bot]` gets a default, taken from the PR head branch (`head.ref`, `dependabot/<ecosystem>/…`): `github_actions` → `none`, any other ecosystem → `patch` (runtime dependency). It is recorded in the receipt as `impactRaw: "dependabot-default"` with an `impactReason` naming the ecosystem and shown as `none (dependabot default)` or `patch (dependabot default)` in the summary. A Dependabot PR whose head branch is missing or does not match `dependabot/<ecosystem>/…`, and an empty or invalid section on a Dependabot PR, still block. The version is the previous one bumped by the maximum impact; `major` from `0.x` → `MAJOR_FROM_ZERO`.
5. Idempotency: the release commit already tagged → `ALREADY_RELEASED` (no-op; a tag without a Release → `RELEASE_MISSING`, apply creates only the Release, with the inventory taken from the next lower ancestor tag so the "Included Issues" block is right). The computed tag on another commit → `TAG_CONFLICT`. All included impacts `none` → `NO_RELEASE`. `## Version impact` lines that name more than one keyword ("minor/patch") are invalid; HTML-comment placeholders, checkbox lists and a heading with a trailing colon are not recognised either (fail closed), so PR templates must keep the plain form.
6. Apply: create the tag ref on the exact SHA, read it back, create the Release with native generated notes plus the "Included Issues" block (from the `Task identity` lines of the included PRs), read it back as published. Any read-back mismatch → `READBACK_MISMATCH`. The Release is marked "Latest" (`make_latest`) only when its tag is the highest `<prefix>X.Y.Z` of the repository; a backfilled lower version never takes "Latest" from a newer one.

Receipt (`--output`, uploaded by the workflow as `release-receipt-<run>`): `contract: chipin-release/v1`, `mode`, `repository`, `strategy`, `trigger`, `sha`, `releaseBranch`, `previousTag`, `includedPullRequests` (`number`, `impact`, `impactRaw`, `taskIdentity`, `mergedAt`), `unattributedCommits`, `impact`, `version`, `tag`, `outcome` (`PLANNED`, `NO_RELEASE`, `ALREADY_RELEASED`, `RELEASE_MISSING`, `RELEASED`, `BLOCKED` + `code`), `detail`. The process exits 1 only for `BLOCKED`.

Callers: the reusable workflow `.github/workflows/release.yml` (`workflow_call`, inputs `ref`, `initial-version`, `apply`; secret `token`) checks out this repository at the SHA the caller pinned (`job.workflow_sha`, verified after checkout; an empty value fails the job) and runs `automation/release-action`. Permissions are inherited from the caller job, which grants `contents: write`; tags and Releases created with the default `GITHUB_TOKEN` do not trigger other workflows (a PAT or App token is needed if something must react to the tag). The templates serialise runs per repository with a `concurrency` group. The inventory relies on `/commits/{sha}/pulls`, which lists merged PRs only for commits reachable from the default branch (true for every registry release branch today). Templates: `templates/caller-release-promotion.yml` (promotion-branch layouts such as the frontend `dev -> main` rollback record; no registered user since [#216](https://github.com/ChipIn-one/.github/issues/216)) and `templates/caller-release-integration.yml` (`.github`-like, push to the integration branch). `.github` adopted the integration template in [#175](https://github.com/ChipIn-one/.github/issues/175) (`.github/workflows/release-on-master.yml`: push to `master`, `apply: true`, pinned to the current org tag SHA, `pull-requests: read` added for the inventory); the frontend `deploy-tag` caller is `.github/workflows/release-on-production.yml` ([chipin-frontend#586](https://github.com/ChipIn-one/chipin-frontend/issues/586), [Frontend specifics](#frontend-specifics)). The caller pins a tag SHA, so a merge that changes the engine is released by the previous engine; the pin is then raised (Dependabot `github-actions` or by hand) and the next merge runs the new one. How to choose the impact of a `.github` PR: [README §4](README.md#4-versioning-and-pins).
