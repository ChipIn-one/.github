For ChipIn issue creation in any registry repository whose `admission` capability is not `off` (FE/BE/KB/`.github`), `gh issue create` alone is not completion. Follow [automation/issue-intake.md](automation/issue-intake.md) and finish explicit canonical Type/Priority/applicable Severity plus exactly one Project #5 membership with readable Status and read-back receipt. Native Milestone is optional release targeting, is preserved as-is, and does not authorize execution or completion. Project #5 Status uses `Backlog`, `Todo`, `In Progress`, `Awaiting release` (written only by the completion engine, never a closure trigger), with `Done` only as a derived mirror of native `closed/completed`; native Issue closure remains terminal authority. Shared UI forms use the manual finalizer described there.

When the active GitHub connector can create ordinary Issues but cannot write Organization Issue Fields / Issue Type / Projects v2 directly, do not stop after raw issue creation or report that canonical completion is impossible. Create the exact connector bridge request documented in [automation/issue-intake.md](automation/issue-intake.md); the bridge must complete the existing canonical intake and return a read-back receipt.

## Canonical Issue admission (org #53, scope by registry since #183)

Admission modes are defined once in [core invariants](docs/workflow/roles/core.md#issue-admission); below are the mechanics.

The authoritative metadata writer is `automation/issue-intake.mjs`. A raw Issue URL, a queued bridge comment, or stale evidence is never admission. The live read-only check is `automation/issue-admission.mjs --issue ChipIn-one/<repo>#<number>` with the appropriate org read credential; a result is bound to the **exact current Issue revision**, is refreshed at each controlled boundary, and expires after 120 seconds. The required owner comes from the registry record (`owner`): FE and `.github` need native `syllik`, BE native `olegbal`, KB (`owner: null`) an explicit `--owner`; other human assignees are preserved. Unavailable org fields, Project #5, permissions, or a mismatched revision produce BLOCKED. Release-milestone control Issues have a separate narrow command and do not grant agent execution authority.

Org infrastructure tasks (`ChipIn-one/.github#N`) use the same path as any other registry repository: `issue-admission-preflight.mjs --issue ChipIn-one/.github#N` (owner `syllik` from the registry, Project #5, native blocker gate), with the semantics of its registry capability. The former per-task "bounded governance bootstrap" (`#53` only) is retired by [#183](https://github.com/ChipIn-one/.github/issues/183); no manual read-back substitutes for admission. External connectors cannot be intercepted at raw GitHub API creation; their *continuation* must stop until the canonical bridge emits a verified `INTAKE_COMPLETE` read-back. This is an intake-completion rule for Issues created through a connector, independent of the target's admission mode. See [automation/issue-intake.md](automation/issue-intake.md).

## Read-only issue-based preflight routing (#119)

Whenever [core invariants](docs/workflow/roles/core.md#issue-admission) call for a preflight (even before a PR exists), use `automation/issue-admission-preflight.mjs --issue ChipIn-one/<repo>#<number>` as the shared read-only entry. It reuses canonical `readAdmission()`; with no injected `GITHUB_TOKEN`, it tries the already-authenticated `gh api` session without extracting credentials. KB requires an explicit `--owner`. For connector-only execution, only an authenticated trusted `.github` producer artifact with authoritative run/source/artifact read-back, original <120s timestamp and full canonical revision can be consumed; ordinary Issue GET and intake-bridge QUEUED are not admission. Reproduce and recheck at every controlled boundary. Executor must not dispatch Actions or repair GitHub metadata. See [automation/issue-intake.md](automation/issue-intake.md). This separate #119 governance approval does not expand the historical #53/PR #57 bootstrap.

## Tests

Run the automation suite with `node --test automation/*.test.mjs` (CI: `.github/workflows/automation-tests.yml`, Node 24.21.0). The short form `node --test automation/` fails on Node 24+ (the directory is treated as a module); do not use it in docs, briefs or PR descriptions.
